# ai-advent-agent — День 8. Настройки модели и диагностика задержки

Учебное задание: CLI-агент на Java, который принимает запросы пользователя
из консоли, отправляет их в LLM через OpenAI-совместимый HTTP API
и выводит ответы в консоль. Агент поддерживает **многошаговый диалог**:
учитываются предыдущие сообщения пользователя и собственные ответы агента,
а история беседы **сохраняется в JSON-файл** и восстанавливается при следующем
запуске — разговор можно продолжить после перезапуска. Это по-прежнему
**не** автономный агент: без инструментов и планирования.

## Стек

- Java 21, Maven
- Jackson (JSON), `java.net.http.HttpClient` (HTTP) — без Spring, SQLite и других фреймворков

## Почему LlmAgent — отдельная сущность

Вся логика общения с LLM инкапсулирована в `LlmAgent`:

- публичный интерфейс — один метод `String ask(String userMessage)`;
- агент **владеет историей беседы**: завершённые пары user/assistant хранятся
  в его внутреннем списке и передаются в API явно через массив `messages`;
- постоянное хранение выделено `ConversationStore`: при создании агент
  восстанавливает из него сохранённую беседу, после каждого успешного ответа —
  сохраняет обновлённое состояние;
- `HttpClient` и `ObjectMapper` создаются один раз в конструкторе и переиспользуются;
- внутри агента: проверка запроса, формирование JSON с полным контекстом
  (`system` → предыдущие пары → новый `user`, каждое сообщение — отдельный объект
  массива `messages`), заголовки (`Content-Type`, `Authorization: Bearer`,
  `x-opencode-session`), отправка, обработка HTTP-ошибок/таймаутов/сети
  и извлечение `choices[0].message.content`;
- обновление истории атомарно: новая пара user/assistant сохраняется **только
  после** успешного ответа и успешной записи в хранилище, поэтому таймаут,
  HTTP-ошибка, некорректный JSON, пустой ответ, прерывание или сбой записи
  не повреждают историю и не создают дубликатов при повторном вводе.

`Main` не знает ни про HTTP, ни про JSON, ни про файлы истории: он только читает
консоль, выполняет локальные команды и печатает `Агент: <ответ>`. Конфигурация
передаётся агенту через `Config`, хранилище — через `ConversationStore`,
глобального состояния нет. Так агент можно переиспользовать в любом другом
интерфейсе (например, в GUI или тестах) без изменений.

## Как работает память диалога

- Первым сообщением каждого запроса отправляется постоянная системная
  инструкция (роль `system`), затем — завершённые пары user/assistant,
  затем — новый запрос пользователя. Пример последовательности ролей
  во втором запросе: `system → user → assistant → user`.
- История не склеивается в одну строку — каждое сообщение передаётся
  отдельным объектом массива `messages`. **Контекст обеспечивает именно
  массив `messages`, а не идентификатор сессии**: заголовок
  `x-opencode-session` требуется шлюзом OpenCode Go для маршрутизации,
  сам по себе он память не обеспечивает.
- В памяти процесса хранятся те же пары user/assistant, что и на диске:
  после каждого успешного ответа состояние сохраняется в JSON, при следующем
  запуске — восстанавливается и включается в запрос к LLM (подробнее
  в разделе «День 7. Сохранение контекста»).

### Ограничение роста контекста

`LlmAgent.MAX_HISTORY_TURNS = 20` — максимум завершённых пар user/assistant
в памяти и в файле истории; столько же последних пар по умолчанию отправляется
в запросе, но отправку можно дополнительно ограничить `LLM_CONTEXT_MAX_TURNS`
(см. раздел «День 8»). Важно понимать:

- это ограничение **числа реплик**, а не точный подсчёт токенов;
- длинные сообщения даже в пределах 20 пар могут превысить контекстное окно
  модели — размер окна намеренно не зашит в код;
- удалённые самые старые пары больше **не отправляются** в API и **не
  хранятся** в файле — они больше не помнятся: ни в рамках запуска, ни после
  перезапуска; вернуть их нельзя;
- повторная передача истории в каждом запросе увеличивает расход входных
  токенов — чем длиннее беседа, тем дороже каждый запрос;
- при удалении старых сообщений соблюдаются целые пары: assistant никогда
  не остаётся без предшествующего user;
- если API откажет из-за размера контекста, агент покажет понятную ошибку
  с HTTP-статусом и **не будет** очищать историю автоматически — сократить
  беседу можно вручную командой `/reset`.

## День 7. Сохранение контекста

Ранее история диалога жила только в памяти и исчезала при выходе. Теперь она
сохраняется в JSON-файл и восстанавливается при следующем запуске: можно
завершить приложение и продолжить беседу позже с тем же контекстом.

### Где хранится история

- По умолчанию: `~/.ai-advent-agent/conversation.json` (домашний каталог
  определяется через системное свойство `user.home`; символ `~` Java сама
  не раскрывает). Путь не зависит от текущего каталога запуска: запускать
  `ai-agent` можно из любой папки — беседа будет одной и той же.
- Переменная окружения `LLM_HISTORY_FILE` задаёт другой файл. Только
  **абсолютный** путь: относительный отвергается с понятной ошибкой, чтобы
  история не «разъезжалась» по разным каталогам запуска.
- Родительский каталог создаётся автоматически; на POSIX-системах каталог
  и файлы получают права доступа только для владельца (`rwx------`,
  `rw-------`). На системах без POSIX-прав приложение продолжает работать
  со стандартными правами.

### Формат и что именно сохраняется

```json
{
  "schemaVersion" : 1,
  "sessionId" : "…uuid…",
  "messages" : [ {
    "role" : "user",
    "content" : "…"
  }, {
    "role" : "assistant",
    "content" : "…"
  } ]
}
```

- `schemaVersion` — версия формата; при чтении принимается только версия 1,
  неизвестная версия даёт понятную ошибку (формат молча не «угадывается»).
- `sessionId` — идентификатор `x-opencode-session`; восстанавливается при
  запуске и меняется после `/reset`. Память диалога он не обеспечивает —
  контекст всегда передаётся массивом `messages`.
- Сохраняются только **завершённые пары** user → assistant после успешного
  ответа модели. Не сохраняются: системная инструкция (она каждый раз
  формируется кодом агента — дублирования после перезапуска нет), служебные
  команды, ошибки, незавершённый ввод, неудачные запросы и внутренние
  рассуждения модели (`reasoning_content`).
- В файл не попадают ключ API, заголовок `Authorization`, содержимое `.env`,
  полные HTTP-запросы и диагностические ответы сервера.
- При чтении проверяются: версия формата, типы и обязательные поля,
  допустимые роли user/assistant, непустой текст, порядок и полнота пар.

### Как работает загрузка и сохранение

- При запуске, до первого запроса: если файла нет — «Начата новая беседа»;
  если есть — файл проверяется, сообщения загружаются в историю агента,
  выводится «Контекст восстановлен: N завершённых обменов». Вся переписка
  автоматически не печатается — посмотреть её можно командой `/history`.
- После каждого успешного ответа новая пара сразу записывается на диск
  (не откладывается до выхода): приложение можно прервать в любой момент —
  всё, на что был получен ответ, уже сохранено.
- Запрос к LLM включает: `system` → восстановленные и новые пары
  user/assistant → новый запрос пользователя.
- При ошибке API, таймауте, некорректном JSON или пустом ответе ни история
  в памяти, ни файл не меняются.
- Если ответ модели получен, но **запись на диск не удалась**, это отдельная
  ситуация: ответ показывается, выводится предупреждение «Ответ получен, но
  не сохранён в контекст…», приложение завершается с ошибкой — продолжать
  беседу с неожиданно неполным контекстом нельзя. Повторный платный запрос
  при этом не выполняется; после перезапуска беседа продолжится с последней
  успешно сохранённой пары.
- Запись безопасная: полный JSON пишется во временный файл в том же каталоге,
  сбрасывается на диск (`FileChannel.force`) и атомарно заменяет основной файл.
  Если атомарная замена не поддерживается файловой системой, прежний файл
  остаётся, а приложение сообщает об ошибке сохранения. Это защищает от
  частичной записи при сбое, но не от любых аппаратных отказов.

### Если файл повреждён

Приложение не удаляет и не «чинит» повреждённый файл и не начинает молча
новую беседу: запуск останавливается с ошибкой, где указан путь. Восстановление
вручную:

1. Переименуйте повреждённый файл, сохранив копию, например:
   `mv ~/.ai-advent-agent/conversation.json ~/.ai-advent-agent/conversation.json.corrupt`
2. Запустите приложение заново — начнётся новая беседа.

Попыток автоматически «починить» переписку с потерей данных не делается.

### Почему нельзя открывать одну историю дважды

Два одновременно запущенных экземпляра не должны перезаписывать одну беседу.
Рядом с JSON создаётся отдельный lock-файл (`conversation.json.lock`), и пока
один экземпляр работает с историей, второй при запуске получает сообщение
«Эта история уже открыта другим экземпляром…» с подсказкой: закрыть другой
экземпляр либо выбрать другой абсолютный путь в `LLM_HISTORY_FILE`. Блокировка
освобождается при выходе (в том числе аварийном); сам оставшийся lock-файл —
не признак активности: занятость определяется реальной файловой блокировкой.

### Пошаговая проверка с перезапуском

Используйте отдельный временный путь истории, чтобы не трогать основную
переписку (значения из `.env` загружаются обычным способом):

```bash
source .env
export LLM_HISTORY_FILE="$HOME/.ai-advent-agent/check-day7.json"

# Первый запуск
ai-agent
#   ввести: Запомни: меня зовут Роман. Для учебного проекта я выбрал
#           кодовое слово "северный маяк" и цвет интерфейса — зелёный.
#           Подтверди кратко.
#   получить ответ, затем: /exit

# Второй запуск (тот же путь истории)
ai-agent
#   должно появиться: «Контекст восстановлен: 1 завершённых обменов.»
#   ввести: Как меня зовут, какое кодовое слово и какой цвет интерфейса я выбрал?
#   ответ должен использовать сведения первого запуска
#   ввести: /history — старые сообщения восстановлены
#   ввести: /reset — новая беседа (сохраняется между запусками), затем /exit

# Третий запуск: после /reset история пуста — «Начата новая беседа.»
ai-agent
```

После проверки удалите временный файл истории:
`rm ~/.ai-advent-agent/check-day7.json*`.

### Важно знать про хранение истории

- История содержит **тексты переписки в незашифрованном виде** — не публикуйте
  её и не коммитьте в репозиторий (имена `conversation.json*` добавлены
  в `.gitignore`).
- Права файла ограничивают доступ других пользователей системы, но **не являются
  шифрованием**: с правами администратора (root) файл может быть прочитан.
- Продолжая беседу, агент **повторно передаёт сохранённые сообщения провайдеру**
  в каждом запросе — учитывайте это для чувствительных данных.

## День 8. Настройки модели и диагностика задержки

Наблюдаемая проблема: запрос «сочини стих…» ожидал ответа около 164 секунд
при модели glm-5.3-flash. Причина по коду не установлена однозначно:
в прежних запросах не было лимита генерации (`max_tokens` отсутствовал),
и модель могла генерировать длинный ответ (включая внутренние рассуждения)
без ограничения. Ускорение **не объявляется достигнутым** — нужны замеры
(сценарий ниже). Доработка делает задержку управляемой и измеримой.

### Профили ответа

| Профиль | `max_tokens` | Особенности |
|---|---|---|
| `fast` | 512 | + предпочтение краткости в системной инструкции |
| `balanced` | 1024 | профиль по умолчанию |
| `detailed` | 2048 | для длинных ответов |

- Выбор профиля: переменная `LLM_RESPONSE_MODE` при запуске или команда
  `/mode fast|balanced|detailed` в чате (действует до конца текущего запуска,
  не вызывает API и не трогает историю).
- `/mode` без аргумента показывает текущий профиль и лимит; если лимит задан
  `LLM_MAX_OUTPUT_TOKENS`, это отмечается — профиль тогда меняет только
  поведение системной инструкции.
- Лимиты — экспериментальные; при обрезании выбирайте профиль подробнее
  или задайте точное значение `LLM_MAX_OUTPUT_TOKENS`.

### Ограничение отправляемого контекста

`LLM_CONTEXT_MAX_TURNS` ограничивает только **отправку**: в запрос уходят
system, последние N завершённых пар user/assistant и новый запрос. Файл
истории и память не урезаются — архив беседы сохраняется по прежней политике
(до 20 пар). Если часть истории не отправляется, после ответа выводится:
«В запрос включены последние N обменов. Более ранние сообщения сейчас
не учитываются». Модель **не помнит** сообщения, которых нет в запросе;
число пар не является токен-бюджетом. Суммаризация не используется.

### Остановка по лимиту и пустой ответ

- Если ответ остановлен по лимиту (`finish_reason: length`) и текст непустой —
  ответ показывается с предупреждением «Ответ мог быть обрезан по лимиту
  генерации…» и подсказкой выбрать `/mode detailed`. Автоматический повторный
  запрос не выполняется.
- Если видимый ответ пуст — понятная ошибка (лимит мог уйти на внутренние
  рассуждения модели), пара в историю **не** записывается, запрос автоматически
  не повторяется.

### Диагностика

При `LLM_DIAGNOSTICS=true` после каждого ответа выводится краткая сводка:
модель, профиль, фактический лимит, число сообщений, размер тела запроса,
времена (`System.nanoTime`): подготовка / HTTP до полного ответа / разбор /
сохранение истории / всего, а также `finish_reason` и `usage`
(`prompt_tokens`/`completion_tokens`/`total_tokens`) по стандартным полям
OpenAI-совместимого ответа. Отсутствующее поле — «нет данных», а не ноль.
Токены по символам не оцениваются, стоимость не вычисляется. Диагностика
не содержит ключа API и текстов переписки. Время HTTP — это время до
**полного** тела ответа, а не «до первого токена»: запрос непотоковый.

### Про streaming

SSE/streaming в этой доработке сознательно не внедрялся — это отдельное
изменение транспорта и UI. Streaming может уменьшить ожидание **первого
видимого текста**, но не гарантирует сокращения полного времени ответа.

### Сценарий сравнительного замера (ручной)

Реальные запросы платные — эксперимент выполняется вручную и по желанию.
Не запускайте без необходимости; одна модель и endpoint, никаких других
изменений между прогонами:

1. Подготовьте две переменные окружения (в дополнение к обычным):

   ```bash
   # вариант A: прежние настройки без лимита генерации
   unset LLM_RESPONSE_MODE LLM_MAX_OUTPUT_TOKENS
   # вариант B: быстрый профиль
   export LLM_RESPONSE_MODE=fast
   ```

2. Для каждого прогона — **своя пустая тестовая история**, чтобы входной
   контекст был одинаковым:

   ```bash
   export LLM_HISTORY_FILE="$HOME/.ai-advent-agent/bench-1.json"   # новый файл на прогон
   ai-agent
   #   запрос: Напиши стихотворение про вайбкодера: два четверостишия, без вступления
   #   при LLM_DIAGNOSTICS=true запишите время «HTTP до полного ответа» и usage
   #   затем /exit
   ```

3. Чередуйте варианты (A, B, A, B, A, B) — по три прогона на вариант,
   снижая влияние нагрузки провайдера.
4. Сравните: медиану полного времени, время HTTP-вызова, фактические
   входные/выходные токены (usage), наличие обрезания (`finish_reason: length`)
   и качество/соответствие стихотворения запросу.
5. Экспериментальная переписка остаётся в файлах `bench-*.json` и не
   смешивается с личной историей; после замера их можно удалить.
6. Если локальные этапы по диагностике быстрые, а HTTP стабильно долгий —
   это повод проверить модель/маршрут провайдера отдельным запросом;
   самостоятельно код этого не меняет.

## Настройка окружения

Обязательные переменные (значение по умолчанию у модели отсутствует):

```bash
export LLM_API_KEY="YOUR_API_KEY"   # ключ API (никому не показывать, не коммитить)
export LLM_API_URL="https://opencode.ai/zen/go/v1/chat/completions"
export LLM_MODEL="glm-5.3-flash"
```

Дополнительные переменные (все необязательные, читаются в одном месте —
`ModelSettings`):

| Переменная | Значения | По умолчанию | Что делает |
|---|---|---|---|
| `LLM_RESPONSE_MODE` | `fast`, `balanced`, `detailed` | `balanced` | Профиль ответа: лимит генерации (`max_tokens`) 512/1024/2048 и предпочтение краткости в `fast` |
| `LLM_MAX_OUTPUT_TOKENS` | целое > 0 | не задано | Явный лимит генерации; **приоритетнее профиля** — `/mode` его не меняет |
| `LLM_TEMPERATURE` | число 0…2 | не задано | Temperature; без переопределения поле в запрос не отправляется |
| `LLM_REQUEST_TIMEOUT_SECONDS` | целое > 0 | `180` | Таймаут ожидания ответа (ограничивает ожидание, но не ускоряет модель) |
| `LLM_CONTEXT_MAX_TURNS` | целое > 0 | не задано | Сколько последних пар отправлять в запросе; файл истории не урезается |
| `LLM_DIAGNOSTICS` | `true` / `false` | `false` | Краткие метрики каждого запроса |
| `LLM_HISTORY_FILE` | абсолютный путь | `~/.ai-advent-agent/conversation.json` | Файл истории (см. «День 7») |

Приоритет лимита генерации: `LLM_MAX_OUTPUT_TOKENS` → профиль
(`LLM_RESPONSE_MODE` / `/mode`) → `balanced` (1024).

Важно про `max_tokens`: это **верхний предел** генерации, а не обязательная
длина ответа. Его уменьшение ограничивает худший случай (длинные ответы),
но не гарантирует сокращения задержки до первого видимого текста. У моделей
с внутренними рассуждениями часть лимита может уйти на reasoning — тогда
видимый ответ будет короче или пуст (агент предупреждает, см. ниже).
Начальные лимиты 512/1024/2048 — **экспериментальные значения**, а не
проверенные оптимумы для glm-5.3-flash; профиль по умолчанию — `balanced`,
поскольку `fast` (512) на reasoning-модели может давать пустые ответы.

Ключ лежит в локальном файле `.env` в корне проекта (shell-строки `export ...`).
`.env` добавлен в `.gitignore` и не попадает в репозиторий.

> `System.getenv` не загружает файлы `.env` автоматически — их нужно загрузить
> командой `source` перед запуском.

### Запуск одной командой на macOS

Требования: JDK 21+, Maven (или Maven Wrapper `./mvnw` в проекте) и локальный
`.env` в корне с тремя переменными (см. «Настройка окружения»).

Основной способ — одна команда из корня проекта:

```bash
./start-agent.sh
```

Что происходит: скрипт определяет директорию проекта по своему расположению,
открывает **отдельное окно Terminal.app** и запускает в нём внутренний скрипт
`run-agent.command`, который загружает `.env`, проверяет JDK 21+ и Maven
(использует `./mvnw`, если он есть, иначе системный `mvn`), собирает проект
и запускает интерактивный чат. Исходное окно терминала чатом не становится
и завершения диалога не ждёт. IntelliJ IDEA для работы не нужна.

Альтернатива — двойной щелчок по файлу `run-agent.command` в Finder: он делает
то же самое в новом окне Terminal. Если права ещё не выданы, выполните один раз:

```bash
chmod +x start-agent.sh run-agent.command
```

Диагностика (выводится в новом окне, запуск завершается с ненулевым кодом):

- нет JDK 21+ — сообщение с подсказкой установить JDK; скрипт также ищет
  подходящую JDK стандартным инструментом macOS (`/usr/libexec/java_home`);
  JDK, выбранная только в IDEA, оболочке недоступна — нужен установленный
  в системе JDK;
- нет Maven и `./mvnw` — подсказка установить Maven (например,
  `brew install maven`) или добавить Maven Wrapper;
- нет `.env` или пустая обязательная переменная — сообщение с именем файла
  и переменной (значения не печатаются);
- ошибка сборки — полная диагностика Maven, запуск агента не выполняется.

Примечания:

- первая сборка может требовать интернет для загрузки Maven-зависимостей;
- macOS может запросить разрешение на управление Terminal («…хочет
  управлять Terminal») — это штатный механизм безопасности для AppleScript;
  разрешите доступ один раз, системные механизмы безопасности не отключаются;
- скрипты не закрывают и не изменяют другие окна Terminal; окно с агентом
  после завершения остаётся открытым — закройте его вручную (автозакрытие
  зависит от настроек Terminal);
- `.env` загружается через `source`, то есть выполняется как shell-код:
  держите в нём только собственные настройки и не берите такой файл
  из недоверенных источников; `.env` остаётся в `.gitignore`.

## Установка командой ai-agent (текущий терминал)

Однократная установка из корня проекта:

```bash
./install-cli.sh
```

Установщик без sudo: собирает исполняемый JAR со всеми зависимостями
(Maven Shade) и устанавливает команду `ai-agent` в `~/.local/bin`.
Ключ никуда не записывается: launcher при каждом запуске читает локальный
`.env` проекта и передаёт переменные процессу Java через окружение.

Если `~/.local/bin` отсутствует в PATH, установщик выведет инструкцию
(дочерний процесс не может изменить PATH родительского терминала):

```bash
export PATH="$HOME/.local/bin:$PATH"   # текущая сессия
# постоянно (zsh): добавить ту же строку в ~/.zshrc и выполнить: source ~/.zshrc
```

После настройки PATH команда доступна из любого каталога:

```bash
ai-agent          # интерактивный чат в текущем терминале
ai-agent --plain  # без цветов, спиннера и сложного редактирования
ai-agent --help   # справка по запуску, не требует API-ключа
```

Приложение запускается в текущем терминале, без новых окон; IDEA не нужна.
После выхода вы возвращаетесь в исходный shell с прежним каталогом.
Автоматический упрощённый режим включается при перенаправленном вводе/выводе
и при `TERM=dumb`; переменная `NO_COLOR` отключает цвета.

Важно: установленная команда привязана к директории проекта на момент
установки. Повторный `./install-cli.sh` пересобирает приложение и обновляет
команду; после перемещения проекта нужна повторная установка. Если JAR в
`target/` удалён (например, после `mvn clean`), launcher предложит запустить
установщик заново. Старые скрипты `start-agent.sh` / `run-agent.command`
(отдельное окно Terminal.app) продолжают работать.

При запуске через launcher значения из `.env` имеют приоритет над одноимёнными
переменными текущего shell. `.env` загружается средствами shell (без `eval`)
и исполняет свои строки как shell-код: доверяйте только собственному файлу.

### Интерфейс чата

- При старте — компактный блок: имя, модель, строка профиля
  («Профиль: balanced · лимит генерации: 1024»), информация о восстановленном
  контексте, подсказка команд; экран автоматически не очищается,
  alternate screen не включается — прокрутка средствами терминала работает.
- Приглашение «Вы ›», ответы с заголовком «Агент», пустая строка между
  репликами; ответы печатаются в исходном виде (переносы, отступы,
  Markdown-разметка); управляющие последовательности из текста модели
  обезвреживаются.
- Во время запроса — «Ожидаем ответ…» с реально прошедшим временем и
  спиннером (после ответа или ошибки строка стирается, курсор восстанавливается).
  Токены, стоимость и проценты не имитируются; потоковой генерации нет —
  ответ показывается целиком.

Команды (не вызывают API):

| Команда | Действие |
|---|---|
| `/help` | справка по командам |
| `/history` | история текущего диалога с ролями, включая восстановленную при запуске |
| `/reset` | начать новую беседу (с подтверждением, если история непуста): пустая беседа сначала записывается на диск, затем очищается память; создаётся новый session ID |
| `/clear` | очистить экран, **не** удаляя историю — ни в памяти, ни в файле (отличие от `/reset`) |
| `/multiline` | многострочный ввод |
| `/mode` | показать профиль и лимит генерации; `/mode fast\|balanced\|detailed` — сменить профиль до конца текущего запуска (без вызова API) |
| `/exit` | выход (также `exit`, `quit`) |

Многострочный режим: после `/multiline` все строки считаются содержимым
сообщения; отдельная строка `/send` отправляет накопленный текст одним
сообщением (до этого API не вызывается), `/cancel` отменяет набор,
пустой текст не отправляется. Универсальный Shift+Enter не обещается —
поведение зависит от терминала.

Ввод: редактирование строки, стрелки вверх/вниз — предыдущие введённые
сообщения (история ввода только в памяти), Tab — автодополнение команд.
Ctrl+C на строке ввода отменяет текущий ввод и возвращает новое приглашение;
Ctrl+C во время запроса завершает приложение, возвращая терминал
в исходное состояние (прерывание не отменяет обработку или оплату уже отправленного
запроса у провайдера). Ctrl+D на пустом вводе завершает приложение.
После обычной сетевой ошибки чат можно продолжить.

## Работа с агентом


- Введите запрос и нажмите Enter — агент выведет `Агент: <ответ>` с учётом
  истории беседы (в том числе восстановленной при запуске).
- Локальные команды (без вызова API):
  - `/help` — справка по командам;
  - `/history` — показать сохранённые сообщения с ролями (user/assistant);
    если история пуста, выводится «История диалога пуста.»;
  - `/reset` — начать новую беседу: пустая беседа записывается на диск,
    очищается память и меняется session ID; после перезапуска старая история
    не возвращается; выводит «Начата новая беседа. История очищена.»;
  - `/exit` — завершить приложение.
- Пустая строка пропускается (запрос к API не отправляется).
- `exit` или `quit` — выход без запроса к API. Ctrl+D (EOF) и Ctrl+C также
  завершают приложение. История беседы сохраняется после каждого успешного
  ответа, поэтому выход не требует «сохранить» её отдельно.
- После сетевой ошибки можно ввести следующий запрос; неудавшийся запрос
  в историю не попадает. Автоматических повторов нет — чтобы не создавать
  платные запросы.

- Сборка: `mvn clean package` — успешно.
- Локальный самотест (`SelfTest`, 198 проверок) — все пройдены, без платных

  ```
  [user] Ответь на предыдущий вопрос только названием проекта.
  [assistant] ai-advent-agent
  > /reset
  Начата новая беседа. История очищена.
  > /history
  История диалога пуста.
  ```

  Это реальный результат проверки, а не пример: модель `glm-5.3-flash`
  подтверждена по списку моделей провайдера, запросы завершились успешно,
  ответы на второй и третий вопрос использовали контекст беседы.
  Ранее, при первой версии агента, также был выполнен реальный одиночный
  запрос («Ответь одним словом: столица Франции?» → «Париж»).

## Особенность эндпоинта OpenCode Go

Эндпоинт `/zen/go/v1/chat/completions` (подписка OpenCode Go) требует заголовок
`x-opencode-session` со стабильным идентификатором беседы — без него сервер
возвращает HTTP 400 `MissingSessionID` (см. документацию провайдера
`opencode.ai/docs/go`). `LlmAgent` генерирует UUID при создании новой беседы
и отправляет его в каждом запросе одной беседы; идентификатор сохраняется
в файле истории, восстанавливается при запуске и создаётся заново после
`/reset`. Для обычного эндпоинта `/zen/v1/chat/completions`
этот заголовок не требуется.

Ещё раз: session ID нужен шлюзу для маршрутизации и кэширования, **память
диалога он не обеспечивает** — контекст всегда передаётся явно через массив
`messages` (см. раздел «Как работает память диалога»).
