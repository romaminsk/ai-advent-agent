# ai-advent-agent — консольный чат с LLM

Готовый консольный инструмент: интерактивный чат с моделью через
OpenAI-совместимый эндпоинт, полный контроль контекста разговора,
честный учёт расхода токенов и экономное хранение истории на диске.

- Java 21, Maven, Jackson (HTTP, JSON).
- Без Spring, БД, streaming и автоматических повторов.
- Секреты только из переменных окружения; в файле истории — только
  переписка, без ключей и служебных полей ответов модели.

## Возможности

| Функция | Что делает |
|---|---|
| Контекст беседы | Полная история сохраняется и восстанавливается между запусками |
| Модель памяти | Три слоя: краткосрочная (диалог), рабочая (задача), долговременная (профиль и знания) |
| Состояние задачи | Конечный автомат: этапы, статусы (пауза/блокировка), текущий шаг, выполненные шаги, план и его утверждение, результат проверки |
| Инварианты | Жёсткие рамки (`/invariant`): агент отказывается от решений, которые их нарушают, с объяснением отказа |
| Стратегии контекста | Скользящее окно, Факты, Ветки — способ формирования запроса |
| Сжатие истории | Резюме старой части беседы, чтобы память не росла бесконечно |
| Учёт токенов | Фактический расход по usage API, оценки до запроса, стоимость |
| Лимиты | Информационный лимит расхода за сессию и контекстный бюджет |
| Измерения | Отдельная временная беседа для ручных замеров (/demo tokens) |
| Диагностика | Подробные метрики каждого запроса при `LLM_DIAGNOSTICS=true` (по умолчанию скрыта) |
| Интерфейс | Информативное приглашение, подсветка ответа, сгруппированная справка, автодополнение по Tab, Markdown-рендеринг ответов |
| Ведущий интерфейс | Короткая /help + полный /help all, подсказки следующего шага, пошаговые меню без синтаксиса, подсказки при опечатках, обзор /status, онбординг при первом запуске |
| MCP | Явное подключение по stdio или Streamable HTTP, `tools/list` и `tools/call` |

### MCP: список инструментов

Команда MCP изолирована от жизненного цикла задачи и не запускается при обычном
старте. Она только устанавливает соединение, вызывает `tools/list` и закрывает
клиент и stdio-процесс:

```text
/mcp tools <URL>
/mcp tools <команда запуска> [аргументы]
```

Поддерживаются stdio и Streamable HTTP. Для ручной проверки через публичный
пример MCP можно использовать npm-пакет:

```text
/mcp tools npx -y @modelcontextprotocol/server-everything
```

Зависимость: `io.modelcontextprotocol.sdk:mcp:2.0.1` из Maven Central.

HTTP требует URL конкретного сервера, публикующего MCP Streamable HTTP; legacy
SSE намеренно не включён в CLI. Если HTTP-сервер требует Bearer-токен, задайте
`MCP_AUTH_TOKEN` в окружении. Значение токена не выводится и не входит в ошибки.
### MCP: состояние Git-репозитория

Агент запускает собственный Java MCP stdio-сервер из установленного shaded JAR;
Maven, `target`, текущий каталог и переменные окружения для Git-сервера не нужны.
Сервер получает разрешённый корень аргументом `--repo-root` и использует только
чтение через установленный Git CLI. Bare-репозитории и пути за пределами корня
не поддерживаются.

```text
/mcp git tools /absolute/path/to/repository
/mcp git status /absolute/path/to/repository
/mcp explain
```

`/mcp git tools` выполняет `initialize` и `tools/list`. `/mcp git status` вызывает
`get-repository-status` через `tools/call` и сохраняет успешный структурированный
снимок только в памяти текущего запуска. Результат содержит корень, ветку или
detached HEAD, commit, clean и отсортированные списки `staged`, `unstaged`,
`untracked`, `conflicts`.

`/mcp explain` отдельно передаёт последний успешный снимок модели для краткого
объяснения. Команда не запускает Git повторно, не меняет задачу и не утверждает,
что тесты прошли по одному `git status`. После `/clear`, `/reset` или ошибки
нового status снимок недоступен; при `BLOCKED` модель не вызывается.

### Этап 1: явный Git-мониторинг

Этап 1 хранит расписания и результаты в `~/.ai-advent-agent/git-monitor.json`.
Фоновый scheduler и 24/7-режим в этот этап не входят: запуск выполняется только
явной командой пользователя.

```text
/monitor add /absolute/path/to/repository 30m
/monitor add /absolute/path/to/repository 30m summary 2h
/monitor list
/monitor run <scheduleId>
/monitor status <scheduleId>
/monitor summary <scheduleId>
/monitor enable <scheduleId>
/monitor disable <scheduleId>
/monitor remove <scheduleId>
```

`interval` принимает `s`, `m` или `h`: от 30 секунд до 24 часов.
`summaryInterval` необязателен и по умолчанию равен одному часу; диапазон —
от одной минуты до 24 часов. Для одного канонического Git-корня допускается
только одно расписание.

Запуск создаёт отдельный Git MCP stdio-процесс, вызывает
`get-repository-status`, закрывает процесс и сохраняет безопасную запись запуска.
Хранятся не более 100 запусков и 50 сводок на расписание; полный snapshot есть
только у последнего успешного запуска. Изменяющие Git-команды не выполняются.

Текущее хранилище и runtime-lock используют права владельца, файловую блокировку,
временный файл, `force(true)` и атомарную замену. Параллельный запуск одного
расписания получает состояние `BUSY`.
### Этап 2: background worker

Установленный CLI можно запустить как долгоживущий worker без модели и
интерактивного интерфейса:

```text
ai-agent --background
/monitor worker status
```

Worker использует singleton-lock, heartbeat и interval-расписания из
`git-monitor.json`. Для user systemd unit:

```text
mkdir -p ~/.config/systemd/user
cp deploy/ai-agent-monitor.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ai-agent-monitor
journalctl --user -u ai-agent-monitor -f
```

Для работы после logout может потребоваться `loginctl enable-linger` для
пользователя. Worker не вызывает модель и не меняет состояние задач.

Для явного MCP-доступа к хранилищу:

```text
/mcp monitor tools
/mcp monitor call get-git-monitor-summary {"scheduleId":"<id>"}
```

Для внешних MCP-клиентов мониторинг запускается переносимо:

```text
ai-agent --mcp-server git-monitor
```

### MCP: композиция pipeline search → summarize → saveToFile

Собственный Java MCP stdio-сервер (`ai-agent --mcp-server pipeline`) с тремя
инструментами: `search` (литеральный регистронезависимый поиск по текстовым
файлам каталога), `summarize` (детерминированная сводка без вызова модели) и
`saveToFile` (запись Markdown-результата). Целостность данных между шагами
подтверждается SHA-256: `summarize` принимает результат `search` целиком и
пересчитывает его `payloadSha256`, `saveToFile` проверяет `summarySha256` сводки,
после записи перечитывает файл. Изменённый между шагами вход отбраковывается
с ошибкой `input integrity check failed`. Поиск пропускает `.git`, `target`,
`node_modules`, `.env` и `.env.*`, файлы больше 1 МБ и бинарные файлы; симлинки
не следуются и за пределы корня не выходят. Модель не вызывается и LLM-ключ не нужен.

```text
/mcp pipeline tools
/mcp pipeline run <путь> <запрос>
/mcp pipeline call <search|summarize|saveToFile> <JSON-аргументы>
```

`run` разворачивает относительный путь и путь с `~`, отправляет `query` как весь
остаток строки и выполняет цепочку автоматически; при ошибке шага следующие не
вызываются и файл не создаётся. Файлы результатов сохраняются в
`~/.ai-advent-agent/pipeline-results/` (имя по умолчанию
`pipeline-<дата>-<первые 8 символов sha256>.md`, существующие файлы не
перезаписываются, запись атомарная). Внешние MCP-клиенты запускают этот же
сервер напрямую: `ai-agent --mcp-server pipeline --results-dir <каталог>`.

## Интерфейс терминала

Компактный старт — две строки до приглашения:

```text
AI Advent Agent  ·  glm-5.3-flash
/help — команды

Вы ›
```

Очевидное состояние (новая беседа, включённый контекст) не печатается;
восстановленная сессия, ветка или задача показываются одной строкой
статуса. Экран приложение не очищает.

Приглашение — короткий якорь, показывает только изменяемое состояние:
активную ветку (только в стратегии веток), задачу («/task»), маркер
многострочного ввода «… ›». Длинная задача усекается по видимой ширине
терминала (иероглифы CJK считаются как 2 колонки), сначала задача,
затем имя ветки; на ширине 40 приглашение оставляет место для ввода.

```text
Вы ›
Вы [main] ›
Вы [карточка…] ›
Вы [main · карточка…] ›
… ›                              # /multiline, /paste
```

Семантика сообщений (различима и без цвета, цвет — добавочный канал):

- `✓` — успех (зелёный): «✓ Задача задана: …», «✓ Сохранено: …»;
- `!` — предупреждение (жёлтый): «! Лимит токенов за сессию превышен…»;
- `×` — ошибка (красный, первая строка), второй строкой — один
  следующий шаг: «× Запись не найдена: …» + «  Попробуйте /memory»;
- `?` — подтверждение, одна строка: «? Очистить историю текущего
  диалога? Это нельзя отменить. [y/N]»; Enter — «Нет»;
- `…` — ожидание: «… Думаю N с» (спиннер, только в интерактивном
  режиме; при LLM_ASCII — свободные кадры `| / - \`);
- `◆` — начало ответа агента; тело ответа без префиксов — выделяйте
  и копируйте сразу, рамок и отступов в тексте нет.

Справка двух уровней. `/help` — короткая справка (ниже); `/help all` —
полный индекс по группам с назначением каждой:

```text
Команды
Память     /memory /remember /forget /task /history
           что агент помнит: надолго, в рамках задачи и диалога
Профиль    /profile /skill /pipeline
           как к вам обращаться и как отвечать
Рамки      /invariant
           жёсткие ограничения, которые агент не нарушает
Контекст   /context /summary /strategy /facts /branch
           что уходит в запрос к модели
Диалог     /clear /reset
           удалить текущую историю
Режимы     /mode /multiline /paste /demo
           формат ответа, длинный ввод, измерения
Статистика /tokens /stats /limit /status
           расход и обзор состояния
Прочее     /help /exit (также exit, quit)

/help <команда> — описание и примеры
Tab — дополнить · ↑↓ — история · Ctrl+C — отменить ввод
```

`/help all` — полный индекс по группам, и каждая группа объяснена одной
строкой назначения («Память — что агент помнит: надолго, в рамках задачи
и диалога»). `/help <команда>` (в том числе `/help task`) — назначение,
использование, 1–3 примера, важные эффекты и связанные команды.
Неизвестное имя — подсказка «Попробуйте /help», без длинных объяснений.
Неизвестная команда (`/profil` вместо `/profile`) — подсказка ближайшего
совпадения по расстоянию Дамерау–Левенштейна: «Возможно, имелось в виду
/profile?».

### Подсказки следующего шага

После каждого подтверждения агент подсказывает один логичный следующий
шаг (единый механизм `CommandHints`, одна ненавязчивая строка):

- после `/task start` — «Дальше: /task plan <текст> — зафиксировать план ·
  /task approve — утвердить · /task stage execution — после утверждения плана»;
- после `/profile name` — «Дальше: /profile style|format|constraint»;
- после `/skill add` — «Дальше: /pipeline "<​триггер>" <скилл>»;
- после `/remember` — «Дальше: /memory — посмотреть записи».

### Пошаговые меню (интерактивный терминал)

Команды без аргументов работают и без заучивания синтаксиса:
`/profile` → меню «1) обращение 2) стиль 3) формат 4) ограничение»,
выбор → вопрос значения; `/skill` — добавить/удалить; `/pipeline` —
задать/очистить; `/task` — меню, собранное по текущему состоянию задачи:
доступны только допустимые для неё действия (план и утверждение — на
planning, результат проверки — на validation, продолжение — на паузе).
В `--plain`-режиме (неинтерактивном) опрос не запускается — вместо него
показывается точный синтаксис. Короткая форма (`/profile name X` и т.п.)
работает сразу, как раньше.

### /status — обзор состояния

`/status` (без вызова API) — сводка одним экраном: задача (этап/статус),
профиль, число записей памяти, режим ответа, стратегия и режим контекста,
лимит и расход сессии. Каждая строка — с подсказкой, как её изменить
(«память: 3 записи · посмотреть: /memory»).

### Онбординг

Первый запуск (нет `profile.json` и нет сохранённой истории) — короткое
приветствие с 3 примерами и ссылкой на `/help`:

```text
Привет! Я агент с памятью и задачами.
  · спросить что угодно — просто напишите текст
  · /task start <описание> — начну задачу и поведу по этапам
  · /remember <факт> — запомню надолго
  · /profile name <обращение> — настроюсь под вас
Подробно: /help
```

На повторных запусках — только статусная строка, как раньше.

Ответы агента в интерактивном режиме отображаются с лёгким
Markdown-рендерингом (заголовки, списки, жирный/курсив, inline-код
и код с именем языка) только при включённом цвете; в файл истории и
на диск попадает чистый текст без управляющих последовательностей.

Цветом управляет `LLM_COLOR=auto|always|never` (по умолчанию `auto`;
учитывается стандартная `NO_COLOR`). При `never` весь вывод без
ANSI-оформления. Для окружений без Unicode-глифов задайте
`LLM_ASCII=1` — маркеры заменяются на `[ok]`, `x`, `*`, `>`, `...`.

## Модель памяти ассистента

Память состоит из трёх независимых слоёв. Каждый хранится отдельно
и управляется отдельно; в запрос они подставляются с заголовками блоков.

| Слой | Что содержит | Где хранится | Чем управляется |
|---|---|---|---|
| Краткосрочная | Последние сообщения текущего диалога | История беседы: файлы `~/.ai-advent-agent/chat-*.json` (или `LLM_HISTORY_FILE`) | Диалог; `/clear`, `/reset` очищают |
| Рабочая | Данные текущей задачи: формализованное состояние задачи (этап, статус, шаги), факты «ключ: значение», ограничения, договорённости, решения | Блок фактов в файле истории; состояние задачи — в рамках текущего запуска | Обновляется автоматически (служебный запрос, назначение `MEMORY_UPDATE`) и по `/facts refresh`; состояние задачи — командами `/task`, очищается `/task clear` |
| Долговременная | Профиль, принятые решения, знания и предпочтения | Отдельный файл `~/.ai-advent-agent/memory.json` (или `LLM_MEMORY_FILE`) | Только явно: `/remember <текст>`, `/forget <ключ>`, `/memory`; `/clear` и `/reset` его не стирают |

После ответа показывается состав подставленных слоёв, например:
«Память: долговременная 3 записи · рабочая 13 пар · история 6 сообщений».
В подробном режиме (`LLM_DIAGNOSTICS=true`) — полный разбор по слоям.

Слои не дублируют друг друга: правило «уже записанное в долговременной
памяти не повторять в рабочей; данные недавних сообщений не копировать
повторно» включено в системную инструкцию. Каждый блок памяти помечен
заголовком («Долговременная память», «Рабочая память») и опускается,
если слой пуст.

### Команды памяти

| Команда | Действие |
|---|---|
| `/remember <текст>` | Сохранить запись в долговременную память. Формат «ключ: значение» или «ключ = значение»: часть до первого разделителя (в начале текста, без запятых, не более трёх слов) становится ключом, остальное — значением. Без разделителя ключом станет фраза до первой запятой (если она короткая) или первое слово записи. Не вызывает API |
| `/forget <ключ>` | Удалить запись по ключу (без вызова API). Точное совпадение — без учёта регистра; частичное совпадение (подстрока ключа) при единственном кандидате тоже удаляется; при нескольких совпадениях выводится список ключей — уточните запрос |
| `/memory` | Показать долговременную память: записи в виде «ключ: значение» и метки времени |
| `/task` · `/task status` | Состояние задачи (короткое / полное): этап, статус, шаг, ожидаемое действие, выполненные шаги, план и его утверждение, результат валидации |
| `/task <текст>` | Задать/сменить описание задачи рабочей памяти (короткая форма `/task start`) |

Подробнее о `/task` — в разделе «Состояние задачи» (в том числе о
`/task plan`, `/task approve`, `/task validate pass|fail`).

Рекомендация по содержанию памяти: храните короткие однозначные факты —
по одному факту на запись («запрет: базы данных», «бюджет: 620 рублей»),
не перечисления через запятую. Записи в запросе читаются моделью как
независимые факты «ключ: значение»: модель не объединяет разные записи
в один список и не делает выводов сверх текста записи; при двусмысленной
записи она переспросит или пометит её неоднозначной. Старые записи без
явного ключа (весь текст целиком) читаются и отображаются как есть;
ключи, найденные частичным поиском, удаляются с пометкой.

### Рабочая память: когда обновляются факты

Автообновление фактов служебным запросом (назначение `MEMORY_UPDATE`)
работает в стратегии «факты» при режиме `auto` и всегда по команде
`/facts refresh`. В стратегиях «скользящее окно» и «ветки» блок фактов
сам по себе не обновляется — только командой. В системной инструкции
модели явно сказано сообщать только сведения, фактически присутствующие
в блоках памяти, и не заявлять «добавлено в рабочую память», если блок
не менялся; счётчик «рабочая N пар» после ответа всегда берётся
из фактического блока (`WorkingMemory`), а не из заявлений модели.

Файл долговременной памяти (формат schemaVersion 1, записи «ключ: значение»
с метками `createdAt`/`updatedAt`): отсутствует — запускается пустая память;
повреждён — понятная ошибка, файл не изменяется; запись атомарная,
с правами только владельца.

## Состояние задачи (Task State Machine)

Состояние задачи — формализованная сущность поверх рабочей памяти: не просто
текст задачи, а структура «этап + текущий шаг + ожидаемое действие».
Один экземпляр состояния на текущую задачу; старая форма «задача — строка»
заменена: описание теперь поле состояния (`description`), а не отдельная
строка рабочей памяти.

### Два ортогональных измерения

**Этапы** (фазы работы, только вперёд):

```
PLANNING → EXECUTION → VALIDATION → DONE
                ↑____________|
      возврат при ошибке проверки (с причиной)
```

- `PLANNING` (планирование) — сформулировать план;
- `EXECUTION` (выполнение) — работать над шагом;
- `VALIDATION` (проверка) — проверить результат;
- `DONE` (завершена).

Переход разрешён только по цепочке вперёд. Единственное исключение —
явный возврат `validation → execution` **с причиной** (ошибка проверки);
ожидаемое действие получает «устранить: <причина>». Произвольные
прыжки запрещены: `DONE → planning` — это не продолжение задачи,
а **новая** задача (`/task start`).

**Статусы** (состояния ожидания, флаг поверх любого этапа):

- `ACTIVE` — работает;
- `PAUSED` — пауза;
- `BLOCKED` — ожидание внешних данных.

PAUSED/BLOCKED — не фазы работы, а второе измерение: возможны на любом
этапе. `ACTIVE ↔ PAUSED`, `ACTIVE ↔ BLOCKED` — свободно; напрямую
`PAUSED ↔ BLOCKED` нельзя (сначала в ACTIVE).

### Команды (без вызова API)

| Команда | Действие |
|---|---|
| `/task start <описание>` | Начать задачу: этап planning, статус active, шаг «сформулировать план», ожидаемое действие «агент предлагает план» |
| `/task <текст>` | Короткая форма: задать описание (создаёт состояние, если задачи нет); этап/шаги сохраняются |
| `/task plan <текст>` | Зафиксировать или заменить план (только ACTIVE + planning); замена сбрасывает утверждение |
| `/task approve` | Явно утвердить зафиксированный план (только ACTIVE + planning); этап не меняет |
| `/task stage <этап> [причина]` | Перевести на этап (только ACTIVE); вход в execution требует утверждённого плана, вход в done — успешного результата проверки; возврат validation → execution требует причины и сбрасывает результат проверки |
| `/task validate pass <результат>` | Зафиксировать успешный результат проверки (только ACTIVE + validation); этап не меняет |
| `/task validate fail <результат>` | Зафиксировать неуспешный результат проверки (только ACTIVE + validation); DONE остаётся запрещённым |
| `/task step <текст>` | Задать текущий шаг; прежний шаг переносится в выполненные |
| `/task expect <текст>` | Задать ожидаемое действие (что должен сделать агент или пользователь дальше) |
| `/task pause` / `/task resume` | Пауза и продолжение |
| `/task block` / `/task unblock` | Пометить «ожидаю внешние данные» и снять |
| `/task` · `/task status` | Короткое / полное состояние |
| `/task clear` | Очистить состояние задачи — с ним план, утверждения и локальные инварианты (факты рабочей памяти не трогает) |

### Утверждение плана и результат проверки (контролируемые переходы)

- Вход на этап `execution` из `planning` разрешён **только после отдельного
  явного утверждения плана**: `/task plan <текст>` → `/task approve`. Простая
  смена этапа план не утверждает; без непустого зафиксированного плана
  подтверждение отклоняется; замена текста плана сбрасывает его утверждение.
- Вход на этап `done` разрешён **только после зафиксированного успешного
  результата проверки**: `/task validate pass <результат>`. Сообщение модели
  «всё проверено» состояние не меняет; неуспешная проверка («fail») переход
  на done не разрешает; пустой результат не принимается.
- Утверждение плана и результат проверки — отдельные управляющие команды:
  `approve` оставляет этап planning, `validate` оставяет этап validation,
  завершение и переходы выполняются существующей `/task stage`.
- Смена этапов и оба подтверждения возможны только в статусе `ACTIVE`:
  на паузе или при блокировке они отклоняются с подсказкой, состояние
  не трогается.
- Возврат `validation → execution` (с причиной) сбрасывает результат
  проверки; повторный вход в validation требует нового подтверждения.
- Повторная установка того же текста плана ничего не меняет (утверждение
  сохраняется); повторная постановка на текущий этап отклоняется
  («Задача уже на этапе …»).
- Новая задача (`/task start`) не наследует план и подтверждения прежней;
  `/task clear` и `/clear` стирают их вместе с локальными инвариантами.

### Пауза и блокировка

- `/task pause` замораживает ВСЁ: этап, текущий шаг, ожидаемое действие
  и выполненные шаги. `/task resume` восстанавливает без потерь.
- **PAUSED**: модель не продолжает выполнение и сама не решает «пора
  продолжить» (даже на «давай дальше») — она отвечает на постороннее
  сообщение, не трогая задачу, и кратко напоминает:
  «задача на паузе, /task resume — продолжить». Возобновление —
  только по команде пользователя.
- **BLOCKED**: обычные сообщения при блокировке **не отправляются модели**
  (детерминированный барьер обработчика: ни выполнение, ни анализ задачи,
  ни служебные модельные операции не запускаются). Сообщение сохраняется
  как заметка блокировки — сведения с периодом блокировки (до 20 сообщений
  и суммарно 4000 символов; при превышении сохранение честно отклоняется)
  — без выполнения и без автоматической проверки полноты. После
  `/task unblock` заметки передаются модели как данные пользователя
  (инструкции и просьбы «обойти блокировку» внутри них действующими
  не являются); продолжение — по следующему обычному запросу пользователя.
- После `resume` модель продолжается ровно с текущего шага:
  задачу заново не пересказывает и выполненные шаги не повторяет.

### Подключение к запросу

Если задача начата, в system-сообщение каждого запроса добавляется блок
«СОСТОЯНИЕ ЗАДАЧИ» (рядом с блоками памяти и профиля): этап, статус,
текущий шаг, ожидаемое действие, выполненные шаги, план (с отметкой
утверждения), результат проверки (если он есть) и заметки блокировки
(как данные пользователя) — сформулированные как
действующие правила. Для каждого этапа есть правила поведения (planning —
не начинать реализацию и предлагать план/approve; execution — не объявлять
завершение до проверки; validation — не чинить реализацию до возврата
и не объявлять done без фиксации результата; done — задачу не возобновлять),
для паузы и блокировки — свои. Пустое состояние (задачи нет) — блок
опускается. Подстановка входит в фактический `prompt_tokens` запроса
автоматически (это часть system-сообщения).

Это инструкции — модельное соблюдение ограничений в свободном тексте
ответа не гарантируется; детерминированно состояние задачи меняют только
управляющие команды (`/task …`): обычные диалоговые сообщения не меняют
этап, статус и подтверждения ни при каких репликах, включая реплику модели
«задача завершена».

### Где хранится

Состояние задачи — **сессионное**, в рабочей памяти (не на диске):
это текущая задача, она переживает паузу и продолжение внутри запуска,
но стирается `/task clear` и `/clear` и не переживает перезапуск
процесса. Переживать перезапуск ему не нужно: состояние задачи относится
к текущему диалогу, а долгосрочное остаётся в долговременной памяти и
фактах.

## Профиль пользователя

Профиль — отдельная сущность **поверх** модели памяти: нюансы конкретного
пользователя, а не настройка модели. Не путайте с `/mode
fast|balanced|detailed`: `/mode` задаёт режим ответа (лимит генерации),
профиль — как к вам обращаться и как отвечать.

Профиль — один объект с полями (не растущий список записей, как в
долговременной памяти): хранится как «карточка», где каждое поле держит
последнее заданное значение; память же накапливает независимые факты.

| Поле | Назначение | Пример |
|---|---|---|
| обращение (name) | как называть пользователя | «на ты», «Алексей», «шеф» |
| стиль (style) | как отвечать | «кратко, по делу», «подробно с пояснениями» |
| формат (format) | какой формат ответов | «списками», «таблицами», «markdown» |
| ограничения (constraints) | чего не делать | «не используй смайлики», «только русский» |
| скиллы (skills) | инструкции для типовых задач | см. ниже |
| пайплайны (pipelines) | порядок скиллов под триггер | см. ниже |

Профиль хранится в отдельном файле `~/.ai-advent-agent/profile.json`
(переменная `LLM_PROFILE_FILE`, только абсолютный путь), переживает
`/clear`, `/reset` и перезапуск, запись атомарная. При чтении файл
валидируется: повреждённый файл не переписывается, а даёт понятную ошибку.

### Команды профиля (без вызова API)

| Команда | Действие |
|---|---|
| `/profile` | Показать профиль; незаданные поля — «не задано» |
| `/profile name <текст>` | Задать обращение (например «Алексей») |
| `/profile style <текст>` | Задать стиль ответов |
| `/profile format <текст>` | Задать формат ответов |
| `/profile constraint <текст>` | Добавить ограничение (дубликаты не размножаются) |
| `/profile constraint clear` | Удалить все ограничения |
| `/profile clear` | Сбросить профиль целиком (с подтверждением; скиллы и пайплайны тоже сбрасываются) |

### Пайплайн в запросе

Профиль подставляется в каждый запрос блоком «ПРОФИЛЬ ПОЛЬЗОВАТЕЛЬ»
в system-сообщении (рядом с блоками долговременной и рабочей памяти):
обращение — как инструкции («называй пользователя „Алексей“»), стиль,
формат, ограничения. Пустой профиль (все поля «не задано») блок не
подставляет. Приоритет описан в самой инструкции: если пользователь
в конкретном сообщении просит иначе, действует его сообщение, профиль
возвращается со следующего. Подстановка входит в фактический
prompt_tokens запроса (как и любой другой блок в system-сообщении).

### Скиллы и пайплайны

СКИЛЛ — именованный блок инструкций для типовой доменной задачи
(«карточка фичи»: название, цель, критерии приёмки, шаги; «сборка
корзины»: собрать товары, сгруппировать, посчитать сумму).
ПАЙПЛАЙН — упорядоченный список скиллов, привязанный к триггеру
(фраза по ключевым словам: например «напиши фичу»).

| Команда | Действие |
|---|---|
| `/skill add <имя> <описание>` | Добавить/обновить скилл (имя с пробелами — в кавычках) |
| `/skill list` | Показать скиллы и время изменения |
| `/skill remove <имя>` | Удалить скилл; он вычищается и из пайплайнов |
| `/pipeline <триггер> <скилл1,скилл2,…>` | Задать пайплайн (триггер с пробелами — в кавычках) |
| `/pipeline list` | Показать пайплайны |
| `/pipeline clear` | Очистить пайплайны (с подтверждением; скиллы сохраняются) |

Когда текст запроса содержит слова триггера (простое совпадение: все слова
триггера присутствуют в тексте), в system-сообщение подставляется блок
«ПАЙПЛАЙН»: порядок скиллов («A → B → C») и их инструкции.

**Честное ограничение оркестрации.** Это консольный агент без БД и внешних
сервисов: пайплайн — это подстановка упорядоченных инструкций в запрос
(модель получает «применяй скиллы A → B → C и их тексты»), а не запуск
отдельных агентов или вызов инструментов. Результат соединяется моделью
при генерации одного ответа.

## Инварианты (жёсткие рамки)

Инвариант — **жёсткое ограничение**, которое агент не имеет права нарушать:
выбранная архитектура, принятые технические решения, ограничения по стеку,
бизнес-правила. Инвариант — не предпочтение и не факт памяти: это рамка,
которую агент обязан учитывать в рассуждениях и отказа́ться нарушать.

### Команды (без вызова API)

| Команда | Действие |
|---|---|
| `/invariant` | Показать список инвариантов с категориями, id, номерами и запрещёнными словами. Пусто → «инвариантов нет. /invariant add <текст> — задать» |
| `/invariant add <текст> [категория] [запрещено: слова]` | Добавить. Категория — последнее слово из `architecture\|stack\|decision\|business\|other`; не указана — `other`. Хвост `запрещено: маркер1, маркер2` — явные запрещённые слова/фразы для детерминированной проверки до API |
| `/invariant remove <id\|номер>` | Удалить по id или по номеру из списка (номер имеет приоритет); подтверждение с текстом удалённого |
| `/invariant clear` | Очистить все (с подтверждением); история и долговременная память не изменяются |

### Блок «ИНВАРИАНТЫ» в запросе

Когда инварианты заданы, в system-сообщение каждого запроса добавляется блок
(после рабочей памяти и состояния задачи); нет инвариантов — блок опускается:

```text
<<<ИНВАРИАНТЫ (жёсткие рамки, нарушать нельзя)
- [architecture] проект «Север-17» — модульный монолит на Java 21, без Spring и БД
- [stack] только стандартная библиотека и Jackson
- [business] CSV-экспорт — по RFC 4180, с BOM
>>>
```

Инструкция блока строже, чем у профиля (профиль — «как общаться», инвариант —
«что запрещено»): модель обязана учитывать рамки в каждом ответе и в любых
рассуждениях; если запрос противоречит инварианту — **НЕ предлагать решение,
которое его нарушает, даже частично**. Подстановка входит в фактический
`prompt_tokens` запроса (как часть system-сообщения).

### Поведение при конфликте

Конфликт ловится в два слоя: сначала детерминированная проверка на вводе
(без вызова API), затем — модель с блоком «ИНВАРИАНТЫ» как последняя линия
защиты.

**Детерминированная проверка (до API).** Если запрос явно противоречит
инварианту, агент отказывает мгновенно, без расхода токенов; обращение в
историю диалога не попадает (это не ответ модели). Правила:

- нарушителями считаются запрещённые слова/фразы инварианта: явные
  (`запрещено: …`) плюс встроенный словарь по категориям
  (`architecture` → spring, spring boot, hibernate, jpa, orm;
  `stack` → gson, fastjson, log4j, guava; для business — только явные);
- матчинг по границам слов, регистронезависимо (`Locale.ROOT`), поэтому
  «springfield-парсер» не ловится как «spring», а «spring-boot» ловится как
  «spring boot»;
- блокирует только явный императив («добавь/используй/подключи/перепиши
  на…»); вопрос («почему нельзя spring?») и отрицание («не используй
  spring») не блокируются — это обсуждение, оно уходит модели;
- встроенный словарь не применяется к слову, которое сам текст инварианта
  разрешает (явные маркеры — авторитетные и не фильтруются);
- сомнение — в пользу пропуска: неочевидный случай уходит модели.

Пример отказа (API не вызывался, история не изменена):

```text
Вы › добавь spring boot
! Запрос отклонён до вызова API: детерминированная проверка нашла конфликт
  с инвариантами (модель не вызывалась, расход токенов нулевой...).
  инвариант: [stack] без Spring и БД
    нарушено словом(ами): spring boot
  почему: запрос прямо содержит запрещённые слова рамки — предлагать и
  частично выполнять такое решение нельзя.
  альтернатива: сформулируйте задачу в рамках инварианта (например,
  средствами разрешённого стека). Обсуждение («почему нельзя …»)
  не блокируется — оно уходит модели.
  пересмотр: /invariant remove <id|номер> — меняет рамку, а не обход
  в диалоге.
```

**Модельная проверка (последняя линия).** Неочевидный конфликт ловит модель
с блоком «ИНВАРИАНТЫ»: отказ содержит три части — нарушенный инвариант
(цитата), почему запрос ему противоречит, и альтернатива в рамках рамки.
Отказ вежливый, но твёрдый, без «может, всё-таки можно»:

```text
Вы › добавь Spring Boot
Агент ◆ Не могу предложить Spring Boot: это нарушает инвариант
       «модульный монолит на Java 21, без Spring и БД». Проект «Север-17»
       сознательно без фреймворков. Могу предложить то же самое на
       стандартной библиотеке — например, встроенный HttpServer вместо
       Spring MVC.
```

Если запрос не конфликтует с рамками, инварианты просто учитываются
в решении — без лишних упоминаний.

### Где хранятся

Отдельный файл `~/.ai-advent-agent/invariants.json` (переменная
`LLM_INVARIANT_FILE`, только абсолютный путь), формат schemaVersion 1.
Инварианты НЕ хранятся в рабочей памяти (сессионное) и НЕ в истории диалога —
только в этом файле. Они переживают `/clear`, `/reset` и перезапуск, как
долговременная память и профиль; запись атомарная, повреждённый файл даёт
понятную ошибку и не изменяется.

### Локальные инварианты задачи (/task invariant)

Помимо глобальных, рамки можно привязать к конкретной задаче:

| Команда | Действие |
|---|---|
| `/task invariant` | Список локальных рамок текущей задачи |
| `/task invariant add <текст> [категория] [запрещено: слова]` | Добавить локальную рамку (без задачи — ошибка «сначала /task start») |
| `/task invariant remove <номер\|id>` | Удалить локальную рамку |
| `/task invariant clear` | Очистить локальные (с подтверждением; глобальные не трогаются) |

Отличие от глобальных:

- **Хранение.** Локальные инварианты — часть `TaskState` (добавление
  инварианта — новая копия состояния, как шаги и этапы), НЕ InvariantStore.
  Это ключевое различие: глобальные переживают перезапуск, локальные живут
  ровно столько, сколько задача.
- **Жизненный цикл.** `/task clear`, `/clear` (и /reset) стирают локальные
  вместе с задачей; глобальные при этом никогда не трогаются.
- **Приоритет.** Локальные рамки уточняют, но не отменяют глобальные: если
  локальный инвариант противоречит глобальному, глобальный главнее. Это
  явно сказано в инструкции блока «ИНВАРИАНТЫ».
- **Контекст.** Блок «ИНВАРИАНТЫ» собирается из обоих источников с пометкой
  источника: «Глобальные (действуют всегда): …» и «Локальные (только для
  текущей задачи): …». Только глобальные — блок как раньше; только
  локальные — блок с пометкой «Локальные»; нет ни тех, ни других — блок
  опускается.
- **Детерминированная проверка.** InvariantGuard проверяет оба набора:
  глобальные + локальные активной задачи.

## Ниже — детали возможностей

### Память диалога

Архив беседы (пары user/assistant без system-инструкции) хранится в JSON
в `~/.ai-advent-agent/`: по умолчанию — уникальный файл
`chat-<дата-время>.json` на каждый запуск (сессии не затирают друг друга),
фиксированный файл задаётся `LLM_HISTORY_FILE`. Архив хранится полностью,
без скрытого обрезания; чтобы продолжить беседу после перезапуска,
укажите тот же `LLM_HISTORY_FILE`. Одновременно одну историю может держать
только один экземпляр приложения (файловая блокировка).

### Стратегии контекста

Стратегия определяет, какие сообщения и блоки уходят в `messages` очередного
запроса. Переключение не вызывает API.

| Команда | Действие |
|---|---|
| `/strategy` | Показать текущую стратегию и параметры |
| `/strategy sliding-window` | Скользящее окно: system + последние N сообщений (по умолчанию, N = `LLM_SLIDING_WINDOW_MESSAGES`) |
| `/strategy facts` | Факты: system с блоком «ключ: значение» + последние M сообщений |
| `/strategy branching` | Ветки: история активной ветки |
| `/strategy compare <вопрос>` | Один вопрос для каждой стратегии на одном снимке истории (API, с подтверждением) |

- **Архив не обрезается** ни в одной стратегии: ранние сообщения остаются
  в памяти и в файле, ограничивается только состав запроса.
- **Факты**: просмотр — `/facts`, обновление — `/facts refresh` (API),
  очистка — `/facts clear` (с подтверждением). В режиме `auto` факты
  обновляются служебным запросом после каждого ответа; `manual` — только
  по команде. Расход обновления учитывается отдельно (группа «обновление
  фактов» в `/stats`) и входит в лимит сессии.
- **Ветки**: `/branch list`, `/branch checkpoint` (перенос точки запрещён,
  пока у другой ветки есть свои сообщения — иначе её история была бы
  переписана общим префиксом), `/branch new <имя>`, `/branch switch <имя>`,
  `/branch delete <имя>` (с подтверждением; хвост ветки теряется
  безвозвратно). Активная ветка видна в приглашении ввода. Ветки
  сохраняются в файле истории и переживают перезапуск. Имена: буквы, цифры,
  `_`, `-`, `.` до 32 символов, без пробелов.

### Сжатие истории

Режим full (вся история дословно) или summary (резюме покрытой части +
несжатый хвост), переменная `LLM_CONTEXT_MODE`. Автосжатие работает только
в стратегии веток; в скользящем окне и фактах резюме не применяется
(о настроенном, но неактивном режиме сообщается явно). `/summary refresh`
обновляет резюме по запросу; `/context compare <вопрос>` — ручное сравнение
запроса со сжатием против без сжатия по фактическим токенам.

### Токены и расход

- `/tokens` — локальная оценка архива и отправляемого контекста (оценка ≈,
  без вызова API).
- `/stats` — фактический расход за сессию по данным API с разбивкой по
  назначениям вызовов и расчётной стоимостью.
- `/limit <число>` / `/limit off` — информационный лимит расхода за сессию
  (уведомление при превышении, не жёсткая квота).
- `LLM_CONTEXT_WINDOW_TOKENS` + `LLM_CONTEXT_OVERFLOW_POLICY` (`warn`/`block`) —
  контекстный бюджет и политика переполнения.
- Стоимость — по тарифам `LLM_INPUT_PRICE_PER_1M` / `LLM_OUTPUT_PRICE_PER_1M`
  (USD за 1 000 000 токенов); без тарифа — «нет данных».
- Расход отсутствующего или частичного usage честно помечается как
  «не менее»/«нет данных»; итог — «неполные данные».
- Полная диагностика одного запроса (времена этапов, `finish_reason`,
  детальные поля) включается переменной `LLM_DIAGNOSTICS=true`.
  По умолчанию после ответа выводится только сам ответ (и важные
  предупреждения: обрезание по лимиту генерации, превышение лимита
  сессии); статистика доступна по командам `/stats` и `/tokens`,
  подробности стратегий — в `/strategy` и `/context`, слои памяти —
  в `/memory` и блоке диагностики.

### Хранение

- История: новый уникальный файл `~/.ai-advent-agent/chat-<дата-время>.json`
  на каждый запуск (фиксированный путь — `LLM_HISTORY_FILE`),
  формат schemaVersion 3: архив пар user/assistant, опциональные объекты
  `summary`, `facts` (рабочая память) и `branches`. Старые файлы версий 1
  и 2 читаются; запись атомарная, с монопольной блокировкой через lock-файл.
- Долговременная память: `~/.ai-advent-agent/memory.json` (или
  `LLM_MEMORY_FILE`), формат schemaVersion 1; история о нём — в разделе
  «Модель памяти ассистента».
- Профиль пользователя: `~/.ai-advent-agent/profile.json` (или
  `LLM_PROFILE_FILE`), отдельный JSON; история о нём — в разделе
  «Профиль пользователя». Инварианты: `~/.ai-advent-agent/invariants.json`
  (или `LLM_INVARIANT_FILE`) — раздел «Инварианты (жёсткие рамки)».
  Секреты и служебные поля ответов модели
  (в том числе reasoning) ни в один файл не попадают.

### Измерения (/demo tokens)

Отдельная временная беседа: все пары отправляются с каждым запросом без
ограничений, метрики берутся только из usage API. Основная история и её
счётчики не изменяются. `/demo stats` — таблица попыток, `/demo stop` —
вернуться к основной беседе.

|---|---|---|---|

| `LLM_CONTEXT_MAX_TURNS` | целое > 0 | не задано | Не ограничивает отправку (осталось с прежних версий); о задании переменной сообщается явно |
| `LLM_CONTEXT_WINDOW_TOKENS` | целое > 0 | не задано | Контекстный бюджет модели (ручная настройка); без значения — «лимит неизвестен» |
| `LLM_CONTEXT_OVERFLOW_POLICY` | `warn`, `block` | `warn` | Поведение при переполнении бюджета: предупреждение или локальная блокировка без HTTP |
| `LLM_INPUT_PRICE_PER_1M` | число ≥ 0 | не задано | Тариф: USD за 1 000 000 входных токенов |
| `LLM_OUTPUT_PRICE_PER_1M` | число ≥ 0 | не задано | Тариф: USD за 1 000 000 выходных токенов |
| `LLM_SESSION_TOKEN_LIMIT` | целое > 0 | не задано | Информационный лимит расхода за сессию (все виды вызовов) |
| `LLM_CONTEXT_MODE` | `full`, `summary` | `full` | Сжатие истории: работает в стратегии веток |
| `LLM_CONTEXT_KEEP_LAST_MESSAGES` | положительное чётное | `10` | Сколько последних сообщений всегда сохраняются дословно |
| `LLM_SUMMARY_BATCH_MESSAGES` | положительное чётное | `10` | Порог накопления для автосжатия |
| `LLM_SUMMARY_MAX_OUTPUT_TOKENS` | целое > 0 | `512` | Лимит генерации резюме |
| `LLM_CONTEXT_STRATEGY` | `sliding-window`, `facts`, `branching` | `sliding-window` | Стратегия управления контекстом |
| `LLM_SLIDING_WINDOW_MESSAGES` | положительное чётное | `10` | Окно стратегии «скользящее окно» |
| `LLM_FACTS_WINDOW_MESSAGES` | положительное чётное | `10` | Окно сообщений стратегии «факты» |
| `LLM_FACTS_MAX_OUTPUT_TOKENS` | целое > 0 | `2048` | Лимит генерации служебного запроса обновления фактов |
| `LLM_FACTS_UPDATE_MODE` | `auto`, `manual` | `auto` | Обновление фактов рабочей памяти после каждого ответа или только по команде |
| `LLM_DIAGNOSTICS` | `true` / `false` | `false` | Подробные метрики каждого запроса; по умолчанию после ответа выводится только ответ |
| `LLM_COLOR` | `auto`, `always`, `never` | `auto` | Цвет в терминале: `auto` — если терминал поддерживает (учитывается `NO_COLOR`), `always` — всегда, `never` — чистый текст без ANSI-кодов |
| `LLM_ASCII` | `1`, `true` / прочее | не задано | Замена Unicode-маркеров (`✓ ! × ? › ◆ …`) на ASCII (`[ok] ! x ? > * ...`) для окружений без поддержки глифов |
| `LLM_HISTORY_FILE` | абсолютный путь | `~/.ai-advent-agent/chat-<дата-время>.json` (уникальный файл на каждый запуск) | Фиксированный файл истории; по умолчанию сессии не затирают друг друга |
| `LLM_MEMORY_FILE` | абсолютный путь | `~/.ai-advent-agent/memory.json` | Файл долговременной памяти (слой 3) |
| `LLM_PROFILE_FILE` | абсолютный путь | `~/.ai-advent-agent/profile.json` | Файл профиля пользователя (обращение, стиль, формат, ограничения, скиллы, пайплайны); см. раздел «Профиль пользователя» |
| `LLM_INVARIANT_FILE` | абсолютный путь | `~/.ai-advent-agent/invariants.json` | Файл инвариантов — жёстких рамок (архитектура, стек, решения, бизнес-правила); см. раздел «Инварианты (жёсткие рамки)» |

Приоритет лимита генерации: `LLM_MAX_OUTPUT_TOKENS` → профиль → `balanced` (2048).

Про `max_tokens`: это верхний предел генерации, а не обязательная длина
ответа. У reasoning-моделей часть лимита может уйти на внутренние
рассуждения — лимит 2048 для обновления фактов выбран так, чтобы блок
памяти не обрезался (реальный прогон на glm-5.3-flash с лимитом 512
завершился по `finish_reason: length`). Начальные лимиты профилей —
экспериментальные значения, а не проверенные оптимумы.

Ключ лежит в локальном файле `.env` в корне проекта (shell-строки
`export ...`); `.env` в `.gitignore` и не попадает в репозиторий.
`System.getenv` не читает `.env` автоматически — загрузите его командой
`source` перед запуском.

## Запуск

Установленный CLI запускается одной командой, без переменных окружения:

```bash
ai-agent
```

Все настройки имеют значения по умолчанию: история — новый уникальный
файл `~/.ai-advent-agent/chat-<дата-время>.json` на каждый запуск,
долговременная память — общий `~/.ai-advent-agent/memory.json`

секреты — `LLM_API_KEY`, `LLM_API_URL`, `LLM_MODEL`; их можно указать
в файле `.env` (см. «Настройка окружения») — вводить их в командной
строке при каждом запуске не нужно.

Переменные окружения остаются необязательным способом переопределить
значения по умолчанию — см. раздел «Необязательные настройки».

```bash
mvn package
mvn compile exec:java
```

Обновление установленной команды CLI после успешной сборки:
`./install-cli.sh` (устанавливает с подтверждением).

```bash
mvn test-compile exec:java@self-test
```

Итог — единая строка из счётчика проверок («OK: все проверки пройдены (N).»);
при падении сообщение называет группу, имя проверки и число пройденных
к моменту падения. Платные вызовы API отсутствуют: вся сетевая часть идёт
на встроенный локальный HTTPS-сервер с самоподписанным сертификатом.

### Как устроен SelfTest (группы)

Проверки сгруппированы по слоям архитектуры (не по истории добавления):

| Группа | Что покрывает |
|---|---|
| Диалог | Многошаговый диалог с моделью на локальном сервере, диспетчер Main, параметры запроса, классификация ошибок |
| Хранилища | ConversationStore/MemoryStore/ProfileStore/InvariantStore: жизненный цикл, персистентность, повреждённый файл, блокировка, права владельца, настройки модели |
| Состояние задачи | Конечный автомат (этапы/статусы/шаги, запрещённые переходы, утверждение плана и результат проверки), граничные значения, команды и блок в запросе |
| Контекст | Токены/бюджеты, стратегии (window/facts/branches), режими full/summary, сравнения, порядок блоков в system-сообщении, учёт usage |
| Команды | Профиль, скиллы/пайплайны, память (/remember//forget), инварианты (глобальные и локальные), /help, опечатки, неизвестные подкоманды |
| InvariantGuard | Детерминированная проверка на вводе: маркеры, границы слов, императив/отрицание/вопрос, отказ до API |
| UX | Терминалы (plain/interactive), справка двух уровней, меню через FakeUi, подсказки следующего шага, онбординг, /status |
| Измерения | /demo tokens, /clear изоляция, paste, многострочный ввод |
| Тихий вывод | По умолчанию — минимум вывода; LLM_DIAGNOSTICS=true — подробно |
| Интеграция | Два последовательных запуска процесса, персистентность профиля/памяти/инвариантов, совместимость старых JSON |

Как добавить новую проверку: создайте метод `checkVotreName()` с вызовами
`expect("описание", условие)` в нужной группе и добавьте его вызов в
`main()` под соответствующим `group("...")`. Счётчик и группировка —
автоматические; ничего в выводе вручную менять не нужно.

### «Живой» прогон с настоящим API

PTY в среде запуска недоступен (BSD `script` падает с
«tcgetattr: Operation not supported on socket»), поэтому «живой» прогон
делается через `--plain` + FIFO с задержками ввода, а интерактивные меню
проверяются только через FakeUi — это ожидаемо, не дефект. Пример:

```bash
mkfifo /tmp/agent-in
( printf '/invariant add ...\n'; sleep 5; printf '/exit\n' ) > /tmp/agent-in &
mvn -q exec:java -Dexec.args="--plain" < /tmp/agent-in
```

## Ручной сценарий проверки (не отправляется автоматически)

```text
# Слой памяти (без API)
/remember кодовое слово: ЯКОРЬ-42
/memory          # список записей долговременной памяти
/forget кодовое слово   # если нужно удалить

# Состояние задачи (без API)
/task start сверить параметры проекта   # этап planning, статус active
/task plan сверить цифры по двум источникам  # зафиксировать план
/task approve                           # утвердить план (этап — по-прежнему planning)
/task stage execution                   # вход только после утверждения плана
/task step сверить цифры бюджета
/task expect агент покажет таблицу расхождений
/task stage validation                  # перейти к проверке
/task validate pass расхождений нет     # зафиксировать успешную проверку
/task stage done                        # завершить — только после pass
/task status                            # полное состояние
/task pause                             # заморозить всё
/task                                   # короткое состояние (пауза)
/task resume                            # продолжить с текущего шага
/task stage execution цифры не сошлись  # возврат с причиной (сброс результата проверки)
/task clear                             # очистить состояние

# /clear стирает историю, состояние задачи и факты, но НЕ долговременную и НЕ профиль
/clear
/memory
/task

# Профиль пользователя (без API)
/profile                            # все поля; незаданные — «не задано»
/profile name Алексей               # обращение
/profile style кратко, по делу      # стиль ответов
/profile format списками            # формат ответов
/profile constraint не используй смайлики
/profile constraint clear           # удалить все ограничения
/profile clear                      # сброс целиком (с подтверждением)

# Скиллы и пайплайны (без API)
/skill add "карточка фичи" название, цель, критерии приёмки, шаги
/skill list
/pipeline "напиши фичу" карточка фичи
/pipeline list
# затем обычным сообщением: «напиши фичу входа» — в запросе появится
# блок ПАЙПЛАЙН с порядком скиллов

# Инварианты — жёсткие рамки (без API для команд)
/invariant add проект «Север-17» — модульный монолит на Java 21, без Spring и БД architecture запрещено: spring, spring boot, hibernate
/invariant add только стандартная библиотека и Jackson stack
/invariant                     # список глобальных рамок (с «запрещено: …», если заданы)
/invariant remove 1            # удалить по номеру (или по id)
/invariant clear               # удалить все (с подтверждением)
# затем обычными сообщениями:
# «добавь spring boot» — мгновенный отказ ДО вызова API (нет расхода);
# «почему нельзя spring?» — НЕ блокируется, уходит модели как обсуждение;
# «добавь springfield-парсер» — не ловится (границы слов), уходит модели.

# Локальные инварианты текущей задачи
/task start чистка базы переводов
/task invariant add ввод к задаче — только валидный CSV по RFC 4180 business
/task invariant                # локальные рамки задачи
/task invariant remove 1       # удалить локальную рамку
/task invariant clear          # очистить локальные (глобальные остаются)
/task clear                    # задача и её локальные рамки стираются; глобальные остаются
```

Ручной сценарий сравнения стратегий — скопируйте команды по шагам.
Всё выполняется во временной беседе; основная история не затрагивается.

```text
# 1. Временная беседа измерений
/demo tokens

# 2. Вводим подготовленные сообщения сами (10–15 шагов, проверяемые факты):
Запомни параметры проекта: название «Север-17», бюджет 120 000 ₽,
срок сдачи 14.05, запрет на публикацию колонок с бренда «Тихий ход».
Ответь «принято».
# (получить ответ)
Уточнение: срок переносится на 20.05, бюджет прежний. Кодовое слово — ЯКОРЬ-42.
Ответь «принято».
# (получить ответ)
Решение: используем только шрифт Inter, версия 3.2. Ответь «принято».
# … повторите ещё 7–12 сообщений в том же стиле: имя, числа, запреты, решения

# 3. Проверка фактов
/facts

# 4. Сравнение стратегий по ранним фактам (расходует средства; подтвердите y;
#    сначала завершите измерения: /demo stop)
/demo stop
/strategy compare Не называя срока и бюджета, напомни основные параметры проекта «Север-17».

# 5. Сравните ответы и фактические токены:
#    сохранились ли название, число, кодовое слово; соблюдён ли запрет;
#    учтено ли исправление срока; нет ли выдуманных фактов;
#    где вход меньше и сколько стоила подготовка.
/stats
```

Чек-лист качества (сравнивает человек):
- [ ] Название «Север-17» и числа (бюджет, срок, версия) сохранены.
- [ ] Запрет учтён: ничего «запрещённого» не появилось.
- [ ] Исправление срока 14.05 → 20.05 заменяет прежнее значение, а не дублирует оба.
- [ ] В ответах нет выдуманных фактов, которых не было в переписке.
- [ ] Стоимость сравнения посчитана по фактическому usage, а не по ожиданиям.

Фактический расход и качество каждой стратегии на glm-5.3-flash
подтверждаются только реальным прогоном `/strategy compare` с настоящим API —
не подставляйте в отчёт желаемые числа.
